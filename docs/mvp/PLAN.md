# 当日 MVP 与并行开发流程

目标日：2026-11-04。

最新执行边界：用户后续明确录屏先不开，因此本轮保持采集关闭。观察适配器的合成后端测试与真实 OCR/录屏验收分开；后者待用户在无敏感页面明确启用。当前本地服务和已验证链路见 `handoffs/E.md`。以可运行、可亲自测试的真实闭环为目标，不把今天完成全部长期功能作为承诺。

## 今天交付什么

本人登录 → 输入当前问题 → 发文章或粘贴正文 → DeepSeek 基于来源讨论 → 形成值得讨论的议题 → 本人确认决定 → 补充结果并回看当时理由。桌面通知单独验证；真实观察按用户后续要求保持关闭。

网页承担完整试用；小程序实现同一账号下的聊天、资料提交、议题和决策查看。**两端目标保留**，但小程序尚无 AppID，今天必须分别报告“源码/工具检查/真机联调”状态，不能把网页移动版说成小程序完成。

Wiki.js 必须真实接通；Pensieve 已安装与核验接口，真实观察按用户最新要求暂不启动，不计为已验收。其他链路失败时交付可定位的原因与已完成部分，不用假页面、假采集充数。服务器先交付可复用部署配置与本地运行验证，实际服务器未选，不能报告已上线。

## 执行基线建议

| 部分 | 当日方案及理由 | 边界 |
|---|---|---|
| 后端 | Java 17 + Spring Boot 3.5.x 单体，Maven；PostgreSQL + Flyway | 利用已有背景；一个服务内分模块，不加微服务、Redis、消息队列或独立向量库。补丁版本由 A 锁定并验证。 |
| 模型 | DeepSeek OpenAI 格式 HTTP API，一个可配置模型；默认按现行官方示例 `deepseek-flash` | 模型 ID 可由配置改；真实 key 仅在服务端。先做明确的处理步骤，不新增多 Agent 框架。官方 API 与账号可用性须区分。 |
| 网页 | Vue 3 + Vite + TypeScript，单独模块依赖 | 聊天主界面，来源抽屉、知识/决定/议题页面；避免视觉装饰挤占闭环开发。 |
| 小程序 | 原生微信小程序独立目录，共用后端 JSON 契约 | 微信是当前执行假设；实现薄客户端，不重复模型或记忆逻辑。AppID 创建不阻塞页面代码。 |
| 观察 | Python 本地适配器 + Pensieve 现有能力 | C 先验证真实版本和读取接口；不重写录屏平台。持续观察以进程启停、增量提取和断线恢复为首版重点。 |
| 知识库 | 后端保存资料与出处，Wiki.js 展示主题总结 | A 实现 adapter，E 准备实例；版本与接口按实际实例锁定。不同数据库/凭据与业务服务隔离。 |
| 运行 | 本地 Compose 验证，后续相同镜像部署服务器 | E 负责根配置；不提前购买机器，不占用/改动 TGA 端口和服务。 |

这是可执行的准备方案，不是上述组件已通过实测的声明。选型有实质阻塞时由总控调整一次，并统一更新契约，不让四窗各自换技术。

## 五个角色，四个并行开发窗口

当前对话作为 E 总控；用户新开 A、B、C、D 四个对话。每个角色一份工作区，不能在同一个物理目录互相切分支。

| 角色 | 独占目录 | 第一件可交付的东西 | 后续职责 |
|---|---|---|---|
| A 后端 | `backend/`, `handoffs/A.md` | 迁移、登录、问题/资料/对话 API | 模型、出处、记忆、议题、决定、复盘、Wiki adapter、后端自检 |
| B 网页 | `web/`, `handoffs/B.md` | 登录和主聊天页，按契约接 API | 资料/证据/议题/决定/控制页面与构建 |
| C 观察 | `observer/`, `handoffs/C.md` | Pensieve 版本与真实一条观察的接入证明 | 增量游标、去重、重试、暂停、心跳、桌面通知 |
| D 小程序 | `miniprogram/`, `handoffs/D.md` | 可导入微信工具的登录/聊天入口 | 同一 API 下提交资料、查看议题/决定；记录 AppID 阻塞 |
| E 总控 | 根文件、`docs/`, `deploy/`, `scripts/`, `handoffs/E.md` | 基线、契约、工作区映射 | PostgreSQL/Wiki 实例、环境配置、合并、联调、可运行交付包 |

## 依赖顺序与检查点

1. **G0 共同起点**：基线提交、契约 v1、目录与分支就位后并行开工。现在准备的都是文档，不算应用已开发。
2. **G1 首条链路**：A 先交登录/问题/消息/资料和 job 查询；B、D 使用固定契约样例开发页面，C 独立验证采集。E 同时准备数据库和 Wiki 运行配置。
3. **G2 接真实服务**：A 调通 DeepSeek 与 Wiki；C 经用户开启后上传真实观察；B 接真实 API。来源生成议题，C 接收并显示一条桌面通知。
4. **G3 集成**：总控顺序集成 A → B → C → D，处理跨模块问题。集成后再次跑关键真实链路；每次只集成一个分支，失败修复后继续。
5. **G4 用户试用**：给出实际可打开地址、启动/关闭办法、用户测试表、已验证项与阻塞。小程序 AppID 和实际服务器缺失仍保留在交付说明中。

每个角色先交能连起来的薄实现，再补功能；每达成一个检查点写自己的回执并提交/推送任务分支。不得等全部“打磨完”才第一次联调。时长只能是实际记录，不预填已完成时间或保证几小时成功。

## Git 与协作

- 总控工作区：项目主工作目录，分支 `integration/mvp-20261104`；本机绝对路径见本地开工入口。
- A/B/C/D 使用 `docs/mvp/WORKSPACES.md` 中实际创建的独立 worktree；共同基线通过 Git 核验。
- 根接口及配置只由 E 修改；需求缺口写到各自 `handoffs/<角色>.md`。契约修订后由 E 通知各角色同步，不能靠猜测继续。
- 工作分支提交只包含本角色文件；按用户授权推送到 `origin`。不 force push、不自动合并 PR、不直接提交 main/master。
- E 集成时保护未提交改动，明确要合并的提交，运行验证后推送 integration 分支。最终由用户测试；未经测试不能标“用户验收通过”。

## 外部条件与失败处理

| 条件 | 当前证据 | 不齐时怎么继续 |
|---|---|---|
| DeepSeek key | 本机已配置，真实链路及失败重分析通过 | A 先完成适配与失败状态；E 引导用户写本机忽略的 `.env`，做一次真实请求，不在聊天要求明文 key |
| Docker 服务 | daemon 与本项目五个服务已运行 | E 启动/确认本地运行环境，先检查端口与已有容器；不删已有卷 |
| 小程序账号/AppID | 用户已准备 AppID，并安装登录开发工具；D 导入验收中 | 完成真实工具编译和界面检查；HTTPS/合法域名缺失时手机联网单列待验，不绕过校验 |
| Pensieve | 0.37.0 已安装核验，真实采集关闭 | C 先做只读核验并准备接入；依赖安装不应自动启动长期观察；不可用时及时报阻塞与具体替代方案 |
| Wiki.js | 2.5.317 已配置，真实创建/更新/全文回读通过 | E 准备独立本地实例，A 用实际版本接口验证；无实例时显示 pending_configuration |
| 运行服务器 | 未确定，可考虑 TGA 共机 | E 先测本系统内存/CPU/磁盘，再只读检查候选机；评估端口、隔离、备份后形成部署方案。当前不改 TGA |

成功标准是用户能尝试真实链路。组件未就绪可以交阶段成果，但必须列明哪一段未完成，不能暗中改成只有聊天的 MVP。
